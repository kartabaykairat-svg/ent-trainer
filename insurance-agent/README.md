# Страховой помощник

AI-агент для страхового менеджера: загрузка документов клиента → OCR и
извлечение персональных данных → проверка менеджером → автоматическое
заполнение реальных DOCX-шаблонов договора пенсионного аннуитета и
доверенности → скачивание DOCX/PDF.

Это рабочий MVP (не макет): распознавание идёт через настоящий Tesseract
OCR, заполнение — через настоящие шаблоны АО «КСЖ Nomad Life», проверено
end-to-end тестом (`backend/tests/test_pipeline_e2e.py`) и вручную в
браузере (`frontend/scripts/smoke_test.mjs`).

## Структура

```
insurance-agent/
  backend/                  FastAPI + SQLite
    app/
      services/            OCR, извлечение, слияние/противоречия, расчёты,
                            график выплат, заполнение DOCX, PDF-экспорт,
                            валидация, очистка временных файлов
      routers/              auth, clients, insurance, documents, dashboard
      config/calc_config.yaml   конфигурация формул расчёта (см. ниже)
    templates_source/        ОРИГИНАЛЬНЫЕ, неизменённые файлы менеджера
    templates/                аннотированные копии (см. templates/field_mapping.json)
    scripts/                  annotate_contract.py / annotate_poa.py — как
                               были получены файлы в templates/ из templates_source/
    tests/                    pytest + синтетические тестовые изображения
  frontend/                 React + TypeScript + Vite + Tailwind v4
    src/pages/wizard/         пошаговый процесс: документы → проверка →
                               параметры → расчёт/график → подтверждение
```

Существующее статическое приложение «ENT-тренажёр» в корне репозитория —
отдельный, не связанный с этим проект; он не тронут.

## Деплой на Render (веб-версия по ссылке)

Корневой `Dockerfile` собирает фронтенд и бэкенд в один контейнер — один
URL отдаёт и интерфейс, и API, без CORS/прокси-настроек. `render.yaml`
описывает это как Render Blueprint. Шаги (~5 минут, карта не нужна):

1. Зайдите на [render.com](https://render.com) и зарегистрируйтесь (можно
   через GitHub-аккаунт).
2. **New → Blueprint** → подключите репозиторий `ent-trainer` (Render
   попросит доступ к GitHub при первом разе).
3. Render найдёт `insurance-agent/render.yaml` — если спросит корневую
   директорию, укажите `insurance-agent`.
4. Единственное, что попросят ввести вручную — `SEED_MANAGER_PASSWORD`
   (пароль менеджера для входа в приложение). `SECRET_KEY` и
   `FIELD_ENCRYPTION_KEY` Render сгенерирует сам.
5. **Apply** → сборка займёт 3-5 минут (компиляция фронтенда + установка
   tesseract/libreoffice) → получите ссылку вида
   `https://insurance-agent-xxxx.onrender.com`.
6. Логин — `manager` / пароль, который вы указали на шаге 4.

Бесплатный тариф Render: без карты, но без постоянного диска — база
данных и загруженные файлы сбрасываются при каждом новом деплое (не при
обычном простое/пробуждении). Для реальной работы с клиентами — платный
инстанс с постоянным диском, примонтированным на `/app/storage`, и
`DATABASE_URL`, указывающий на управляемый Postgres вместо SQLite.

Проверено локально (без Docker-демона в этой среде я не мог собрать сам
образ, но подтвердил идентичное поведение): собранный фронтенд, отданный
тем же FastAPI-процессом что и API, с SPA-fallback для клиентских
маршрутов — `insurance-agent/backend/app/main.py`.

## Запуск локально

### Backend

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# сгенерировать и вписать в .env реальные SECRET_KEY и FIELD_ENCRYPTION_KEY:
python3 -c "import secrets; print(secrets.token_urlsafe(48))"
python3 -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
uvicorn app.main:app --reload --port 8000
```

Системные зависимости (уже установлены в этом окружении, для Docker см.
`backend/Dockerfile`):

```bash
apt-get install -y tesseract-ocr tesseract-ocr-rus tesseract-ocr-kaz libreoffice-writer
```

⚠️ Для PDF-экспорта нужен именно `libreoffice-writer`, а не только
`libreoffice`/`libreoffice-core` — без него любая конвертация падает с
`Error: source file could not be loaded`.

При первом запуске автоматически создаётся менеджер
`SEED_MANAGER_USERNAME` / `SEED_MANAGER_PASSWORD` (см. `.env`).

### Frontend

```bash
cd frontend
npm install
npm run dev
```

Vite проксирует `/api` на `http://localhost:8000` (см. `vite.config.ts`).

### Тесты

```bash
cd backend
pytest tests/ -v
```

Полный пайплайн (`test_pipeline_e2e.py`): логин → создание клиента →
загрузка двух синтетических изображений (реальный прогон через Tesseract)
→ проверка извлечённых ФИО/ИИН/даты/адреса → параметры страхования →
подтверждение → генерация договора и доверенности → скачивание DOCX и PDF
→ проверка, что в файлах нет `{{...}}`/`undefined` и есть настоящие
данные клиента → проверка дашборда и маскирования ИИН в истории.

## Как получены шаблоны в templates/

Согласно требованиям проекта, юридический текст исходных файлов
(`templates_source/*_original.docx`) нельзя переписывать. Вместо
программного поиска мест для заполнения "на лету" (что для этих
конкретных, насыщенных подчёркиваниями бланков было бы ненадёжно),
`scripts/annotate_contract.py` и `scripts/annotate_poa.py` один раз
открывают оригиналы и заменяют **только** пустые/предназначенные для
заполнения места на теги `{{ поле }}` (docxtpl/Jinja2), не трогая ни одного
слова остального текста, структуру таблиц, нумерацию пунктов или
форматирование. Результат — `templates/contract_template.docx` и
`templates/poa_template.docx`, которые и использует система заполнения.
Полная карта тегов — `templates/field_mapping.json`, включая явный список
того, что намеренно не тронуто (поля для нотариуса, представителя
страховщика, подписи).

Если оригинальные шаблоны изменятся — запустите скрипты заново, не
редактируйте `templates/*.docx` вручную.

## Расчёт пенсионного аннуитета

Реальная актуарная формула — сертифицированный расчёт с таблицами
смертности, нормой доходности и нагрузками (см. переданный
`templates_source/calculation_reference.xlsm` — это полноценный
актуарный движок на 9 листах, который нельзя корректно
воспроизвести обобщённо). Поэтому:

* возраст и количество лет до целевого возраста считаются всегда
  (чистая календарная арифметика);
* сумма периодической выплаты считается только если в
  `app/config/calc_config.yaml` включена и реализована конкретная
  формула — иначе приложение прямо говорит менеджеру, что нужно ввести
  сумму вручную, а не подставляет что-то придуманное.

## Безопасность (что реализовано, что нет)

Реализовано: JWT-сессии с истечением по времени (автоматический выход),
bcrypt-хеширование пароля менеджера, шифрование всех PII-полей в БД
(Fernet), маскирование ИИН и сокращение ФИО во всех списках, кроме
подтверждённой карточки клиента, журнал действий (`AuditLog`), валидация
типа/размера загружаемых файлов, режим «Удалить документы клиента после
формирования договора», отсутствие публичных URL — файлы отдаются только
через авторизованный API-эндпоинт.

Не реализовано (за пределами объёма MVP, отметить для продакшена):
ролевое разграничение доступа (сейчас один тип пользователя —
менеджер), rate limiting, HTTPS/reverse-proxy настройка, ротация ключа
шифрования, полноценный SIEM-журнал.
